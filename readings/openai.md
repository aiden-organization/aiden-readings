# AI 모델을 업그레이드했다면, 기존 지침도 다시 살펴보세요

*Eric Provencher · OpenAI Developers*

**모델이 발전하면, 과거의 약점을 보완하려고 쌓아둔 지침도 재검토해야 합니다.**

OpenAI는 GPT-6 Astra를 활용할 때 **스킬의 적용 범위, 프로젝트 지침, 승인 경계, 완료 조건**을 점검하라고 권합니다. 오래된 지침이 불필요한 작업을 늘리거나 모델을 일찍 멈추게 할 수 있기 때문입니다. [원문](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)

![GPT-6 Astra를 위한 스킬과 프롬프트 재설계](https://developers.openai.com/images/blog/rethinking-skills-and-prompts-for-gpt-6-astra/cover.webp)

## 01. 스킬 설명은 ‘언제 사용하는가’를 명확하게

스킬은 특정 작업의 지침과 참고자료, 실행 스크립트를 묶은 것입니다. Codex는 먼저 스킬의 **이름과 설명**을 확인하고, 사용할 스킬을 선택한 뒤 본문을 읽습니다.

따라서 설명이 모호하면 관련 없는 스킬이 선택될 수 있습니다. 설치된 스킬이 많으면 초기 목록의 설명이 축약되거나 일부 스킬이 제외될 수도 있습니다.

설명을 작성할 때는 다음을 확인하면 좋습니다.

- 어떤 작업에서 사용하는지 분명한가?
- 핵심 사용 조건이 앞부분에 있는가?
- 다른 스킬과 역할이 겹치지 않는가?

가령 데이터베이스 마이그레이션용 스킬은 ‘데이터베이스 관련 작업’ 전체가 아니라 **마이그레이션 작성·변경·검토**에 적용되도록 범위를 명시합니다. [공식 스킬 문서](https://developers.openai.com/ko-KR/docs/build-skills)

## 02. 상세 설명은 파일로 나누고, 필요할 때 읽게 하기

여러 작업을 지원하는 스킬은 SKILL.md를 간결하게 유지하고, 작업별 상세 설명은 별도 문서로 연결해 필요할 때 읽도록 구성합니다.

예를 들어 보고서 작성 스킬은 다음처럼 구성할 수 있습니다.

```text
보고서-스킬/
├── SKILL.md          ← 작업별 참고자료 안내
├── 데이터분석.md      ← 분석 방법과 계산 기준
├── 차트제작.md        ← 차트 선택과 디자인 지침
└── 보고서작성.md      ← 문서 구성과 표현 방식
```

`SKILL.md`에는 다음과 같이 안내합니다.

> - 데이터 분석이 필요하면 `데이터분석.md`를 읽는다.
> - 차트를 만들 때는 `차트제작.md`를 읽는다.
> - 보고서를 작성할 때는 `보고서작성.md`를 읽는다.
> - 여러 작업이 필요하면 해당 자료들을 읽는다.

기존 `SKILL.md`에 들어 있던 긴 설명은 각각의 파일로 옮기면 됩니다. 이렇게 하면 차트만 만드는 작업에서 보고서 작성법까지 모두 읽지 않아도 됩니다.

**핵심은 AI가 현재 작업에 필요한 설명만 찾아 읽도록 구성하는 것입니다.** 이미 짧고 하나의 작업만 다루는 스킬이라면 굳이 파일을 나눌 필요는 없습니다.

## 03. AGENTS.md의 일괄 지시를 점검하기

오탈자 수정에도 모든 설계 문서를 읽게 하면 작업이 느려집니다. 문서는 필요한 상황과 연결해 안내해야 합니다.

| 기존 지침 | 개선 방향 |
| :--- | :--- |
| 수정 전 모든 문서 읽기 | 서비스 경계·스키마·배포 등 작업별 문서 지정 |
| 세부 절차를 모두 고정 | 필수 조건을 남기고 불필요한 단계 재검토 |
| 검증을 반복해서 요구 | 변경에 필요한 검증 범위 확인 |

저자는 Astra가 스스로 검증하는 경향이 있어, 기존의 반복적인 테스트 지시가 과도한 검증으로 이어질 수 있다고 설명합니다.

## 04. 어디까지 알아서 하고, 언제 멈출지 알려주기

AI에게 일을 맡길 때는 **혼자 진행해도 되는 작업과 사용자 확인이 필요한 작업을 구분해서 알려주는 것**이 좋습니다.

예를 들어 “무엇이든 먼저 물어보고 진행해”라고 하면, 간단한 수정이나 테스트를 할 때도 매번 확인을 요청할 수 있습니다. 반대로 진행 범위를 구체적으로 정해주면 불필요하게 멈추는 일을 줄일 수 있습니다.

또한 **무엇까지 해야 일이 끝나는지**도 알려줘야 합니다. “기능을 만들어줘”라고만 하면, 코드를 작성한 뒤 실제 작동 여부를 확인하기 전에 결과를 보고할 수 있기 때문입니다.

아래처럼 요청하면 진행 범위와 완료 조건이 분명해집니다.

**적용 예시 — 원문 취지를 바탕으로 재구성**

> 기능을 구현하고, 로컬에서 정상적으로 작동하는지 확인해 주세요. 이번 수정 때문에 문제가 생기면 고치고 다시 확인해 주세요. 여기까지는 계속 진행해도 됩니다. 결과를 보고한 뒤, 실제 서비스에 배포하기 전에는 제 확인을 받아주세요.

이 요청은 세 가지를 알려줍니다.

| 구분 | AI에게 알려주는 내용 |
| :--- | :--- |
| **알아서 진행할 일** | 기능 구현, 로컬 테스트, 발생한 문제 수정 |
| **완료 조건** | 기능이 정상적으로 작동하는지 확인하고 결과 보고 |
| **멈추고 확인받을 지점** | 실제 서비스에 배포하기 전 |

처음부터 이 경계를 정해두면, AI가 중간에 불필요하게 멈추거나 사용자가 기대한 확인 작업을 빠뜨리는 일을 줄일 수 있습니다.

---

새 모델을 도입할 때는 **지금도 필요한 규칙인지, 어느 작업에 적용되는지, 어디까지 진행해야 하는지**를 함께 점검해보세요. 팀에서 여러 모델을 사용한다면 같은 지침이 각 모델에 미치는 영향도 고려해야 합니다.
